# 12 源码机制分析（#41286，2026-08-18 晚，2.7.8 tag 逐行核对）

> 状态：**机制链已从源码闭合，运行时验证完成（7 项验证 5 项通过/2 项环境受限），把握度 7–8 成**。本文件回答："我们观测的健康态瞬态，从 WSL 源码机制看，到底是不是 bug、为什么"。
> 源码基线：microsoft/WSL tag 2.7.8（commit 95669d38 "Update kernel to 6.18.33.1-1 (#40728)"，与实测内核 6.18.33.1 一致）。

## 一句话结论

进程内快速 churn 新端口时，Windows 侧 `wslrelay` 的 `StopPortListener` **持全局 SRW 锁同步 `Worker.join()`**，而 worker 退出要等 pending AcceptEx 取消完成（`SingleAcceptHandle` 析构里 `CancelIoEx` + `WSAGetOverlappedResult(fWait=TRUE)`），可能拖 2–5s；期间所有新端口的 `StartPortListener`（含下一次 allocate）在锁上排队 → 新端口注册停滞 → WSL 内 dial 失败 + Windows 侧 curl 不可达，join 完成后自愈。

## 机制链（4 环节，全部有 2.7.8 源码依据）

1. **bind 拦截与延迟注册**：guest 侧 seccomp 只拦 `__NR_bind`（`main.cpp:3572-3576`）。`bind(127.0.0.1, 0)` 时端口未知，`GetCallInfo` 走 `DeferredPortLookup`（`GnsPortTracker.cpp:396-410`）：立即 `CompleteRequest` 恢复进程，**后台** `ResolvePortZeroBind`（532 行）解析端口后才 `HandleRequest` → `RequestPort` → `m_hvSocketChannel->Transaction` **同步等 Windows 回应**。因此 `net.Listen()` 返回时注册可能未完成 → 探针立即 dial 失败的来源。
2. **注销靠 500ms 轮询**：`RunPortRefresh` 每 500ms 用 sock_diag 拉 LISTEN 端口（`GnsPortTracker.cpp:29-58`），close 后最多 500ms 才 `OnRefreshAllocatedPorts` 发 deallocate。
3. **Windows 侧锁内 join**：`StopPortListener`（`wslrelay/localhost.cpp:217-237`）在 `m_lock.lock_exclusive()`（全局 SRW 锁，`localhost.h:60`）内做 `Worker.join()`。`m_RelayThreads` 是**所有端口共享**的 map。
4. **join 慢的来源**：worker（`PortListenerAsync`，301 行）退出时销毁 `SingleAcceptHandle`，析构（`relay.cpp:736-750`）对 pending AcceptEx 执行 `CancelIoEx` + `WSAGetOverlappedResult(fWait=TRUE)` **同步等待取消完成**——时长取决于 Windows 网络栈，静态代码无法证明具体时长（运行时验证目标）。锁被占期间，`RelayWorker` 消息循环里后续 `StartPortListener`（含 allocate(B)）排队。

## 是 bug 吗（正反论证）

**支持缺陷**：
- 持全局锁做 join + 同步等取消，教科书级并发问题；一个端口的慢清理阻塞所有端口注册。
- 触发行为合法且常见：测试框架、port-forward 循环、dev server 重启都会快速 churn 新端口。
- 健康态下新端口 2–5s 不可达不符合合理预期。

**反方（诚实列出）**：
- 官方无 SLA 承诺"新端口立即可达"；自愈、无数据损坏、影响面限于快速 churn。
- 官方可能判定"预期行为"或 low priority。

### 重大发现：本机实际运行的转发实现是闭源 wsldevicehost（Rust consomme），不是开源 wslrelay.exe

**证据链（二进制 + 进程 + 注册表三重确认）：**
1. `netstat` 实测：WSL 内 bind 127.0.0.1:34567 → Windows 侧监听端口由 **dllhost.exe PID 42080** 持有（`C:\Windows\system32\DllHost.exe /Processid:{17696EAC-9568-4CF5-BB8C-82515AAD6C09}`）。
2. `Get-Process -Module`：该 dllhost 只加载 `C:\Program Files\WSL\wsldevicehost.dll`。
3. 注册表：CLSID `{16479D2E-...}` = **WslDeviceHost_Net**，InprocServer32 = wsldevicehost.dll，AppID `{17696EAC-...}` 配置 DllSurrogate（COM 宿主）。
4. 二进制字符串扫描 wsldevicehost.dll（1.6MB，Rust 编写）：源码路径 `hyper-v\wsldevicehost\src\virtio_net.rs`、`oss\vm\devices\net\net_consomme\consomme\src\tcp.rs`，依赖 `smoltcp-0.12.0`、`socket2-0.6.0`、`pal_async`；关键字符串：`proxy_for_guest_port`、`loopback_port`、`Duplicate TCP bind for port`、`virtio-net port request`、`listen_addr`、`127.0.0.1:34254`。**这套实现不在 microsoft/WSL 开源仓库里（闭源）。**
5. 本机**没有运行中的 wslrelay.exe 进程**（程序文件存在 3.4MB，含 PortRelayBind ETW 字符串，但从未被启动）。
6. 之前抓的 Lxss ETW 只有 wslservice 事件、没有 PortRelayBind/UnBind——**原因就是 wslrelay.exe 根本没在跑**，provider 注册了但事件不产生。

**结论**：2.7.8.0 安装版把 localhost 转发做进了闭源 Rust 设备宿主（consomme 用户态 TCP 栈），开源 wslrelay.exe 路径（GnsPortTracker / StopPortListener / SRW 锁 / join / AcceptEx 取消）**不适用于本机运行的实际代码**。之前文档所有基于开源源码的机制推断必须降级为"历史/不适用"，实证观察保留。

### 修正后的实证模型（不再依赖开源源码）

- **正常**：单次注册 ~52ms（guest 侧可达），Windows 侧监听 ~1.3s 出现。
- **症状 A（注册卡顿）**：当**注册与注销在同一 worker 重叠**时，注册概率性卡 2-30s+（churn 第 2 轮起必现；并发双进程也现；与连接历史无关；不单调累积）。机制推断：闭源 consomme 的端口管理 worker 对 register/unregister 串行处理，注销事件（即使 1.3s 快速注销）与注册重叠时处理异常慢。**未直接观测到内部实现。**
- **症状 B（陈旧监听器）**：有连接历史的端口注销时，连接 socket 卡 **CloseWait/FinWait2**，监听器保留 **60-75s** 才移除；期间 Windows 侧该端口 **bind 失败（WSAEADDRINUSE）**、连接旧服务**立即失败**；同端口 in-guest 重启服务正常（relay 复用注册）。多端口注销并行。
- **两症状独立**：悬挂注销不阻塞新注册（V8），但活跃的注销处理会拖慢重叠注册（C3/C4/C5）。

## 阶段四补充 3：T1/T3/T5 决定性实验（2026-08-18 深夜，用户在场）

### 三个新事实（全部对照完备）

**T1 固定 vs ephemeral（关键分水岭）**
- 固定端口 bind：**同步注册**，永远 <1ms 通过（V6 8/8、T1 固定端口 15/15、T3 固定端口 6/6）——注册在 bind 内完成。
- ephemeral（port 0）bind：**延迟注册**，正常 27-52ms；**只有它中招**。
- T1 间隔扫描（ephemeral）：gap 0/200ms 部分卡（1/3、3/3）、500ms 全过、1000/2000ms 全卡——**非单调 = 陈旧累积污染**，不是简单的 close→register 间隔关系。

**T3 卡顿时长分布（90s 超时，排空后干净基线）**
- 8 轮 churn：第 1 轮 52ms OK、第 3 轮 52ms OK，**其余 6 轮 90s 内完全不可达**。
- 关键：第 5-8 轮开始时**陈旧监听器已全部排空**（75s 窗口早已过），仍然 90s+ 卡死 → **churn 的退化是内部状态累积，netstat 不可见**（陈旧监听器只是冰山一角）。
- 此前对外结论"2-5s 自愈"只反映会话早期、低积压状态；持续 churn 后远超 90s。

**T5 剂量响应（1 个 vs 多个陈旧监听器）**
- 0 陈旧：多次对照全部 27-52ms 正常（0/10+ 卡）。
- 1-3 个陈旧：fresh ephemeral 注册 8 次中 3 次卡 >30s。
- 5-6 个陈旧：3/3 全卡 >30s。
- 陈旧监听器**概率性阻塞**新 ephemeral 注册（非确定性）。

### 最终实证模型（v3，不再依赖开源代码）

1. 固定端口 → 同步注册，免疫一切。
2. ephemeral → 延迟注册（27-52ms 正常），与中继的端口管理 worker 交互。
3. 有连接历史的端口关闭后：连接 socket 卡 CloseWait/FinWait2，Windows 监听器保留 60-75s（多端口并行保留），期间 Windows bind 同端口 → WSAEADDRINUSE，连死服务立即失败，同端口 guest 内重启正常。
4. 陈旧监听器数量 ↑ → fresh ephemeral 注册卡死概率 ↑（0% → ~33% → ~100%），单次可 >30-90s。
5. churn 自放大：每轮成功 = 新增 1 个陈旧 → 下一轮更可能卡 → 运行内级联（T3 6/8）。
6. 退化在陈旧排空后仍持续 → 中继内部还有不可见的 per-connection 状态累积（推断，无外部证据）。
7. 跨进程：双进程 churn 双双卡（C5）——"per-process" 论断确认作废。

### 对外结论最终修正清单

1. "self-heals in 2-5 s" → **错误**：持续 churn 后 >90s 不可达；2-5s 只是低积压阶段。
2. "It is per-process, not global" → **撤回**：双进程并发 churn 双双卡。
3. "Source Context: localhost.cpp / UtilAcceptVsock" → **不适用**：本机构建跑的是闭源 wsldevicehost；开源 wslrelay.exe 未运行。
4. 保留正确部分：环境、第 1 轮必过、固定端口对照、无日志、fresh-process 单轮通过（但补充：仅在低积压状态成立）。

### 开源代码机制（本次核验新增，全部带行号）

**C++ 编排（microsoft/WSL master `src/windows/common/ConsommeNetworking.cpp`）**

1. 端口通知入口 `HandlePortNotification`（L212）：guest 端口追踪器（`src/linux/init/localhost.cpp:483` GnsPortTracker，sock_diag 500ms 轮询 + bind 拦截）经 GNS channel 发 allocate/deallocate → 转 Bind/Unbind。
2. **全局独占锁**：`ModifyOpenPorts`（L273）内 `auto lock = m_lock.lock_exclusive()`（L282）→ `device->BindPort(...)`（L290）/ `UnbindPort(...)`（L299）。**所有端口 bind/unbind 串行化**，与旧 wslrelay `StopPortListener` 持全局 SRW 锁同型（设计延续）。
3. bind 失败回滚 `removePort`（L260）：失败时反向 unmap。

**Rust TCP 栈（OpenVMM master `vm/devices/net/net_consomme/consomme/src/tcp.rs`）**

4. `bind_tcp_port`（L708）：listeners map 按 (family, guest_port) 索引；**已占用 → `BindError::PortAlreadyBound`**（L713）——对应 wsldevicehost.dll 内字符串 "Duplicate TCP bind for port"（glue 翻译该错误）。
5. `unbind_tcp_port`（L724）：直接 `e.remove()` 移除 listener（drop 后 Windows 监听 socket 关闭）；未占用 → `PortNotBound`。
6. **TimeWait 计时器未实现**：`FinWait2` 收 FIN → TimeWait（L2021-2022 `// TODO: start timer`）；TimeWait 收包 → `self.ack(sender); // TODO: restart timer`（L2004-2006）。**TimeWait 连接无到期清理**，只能等 poll 层 host socket 错误/EOF 才被 `connections.retain` 移除（L500-541）。
7. loopback 代理：`TcpConnection::new`（L930-990）为 guest loopback 连接创建 host socket `connect()` 到 127.0.0.1:PORT，`loopback_port = ProxyForGuestPort { sending_port, guest_port }`（L981）；`poll_tcp` accept 后按 `sending_port` 反查并替换端口（L428-440）——**同进程自连 + accept 双 socket**，与 netstat 同端口 Listen+CloseWait 并存吻合。

### 对"最初问题"的最终解释（一句话）

> 本机 Consomme 模式下，guest 快速 churn 新端口：每次 bind/close 都要经 guest 500ms 轮询 + GNS 通知 + **全局锁串行的 Bind/Unbind**；有连接历史的端口注销要等连接排空（CloseWait/TimeWait 无定时器），新注册被压在锁后/被陈旧状态拖慢 → Windows 侧新端口低积压时 2-5s、累积后 90s+ 不可达。固定端口同步注册因此免疫；无连接端口快速注销所以会话早期看起来"自愈"。
