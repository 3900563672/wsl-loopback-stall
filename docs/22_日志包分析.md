## 三、决定性证据：失败现场在官方 trace 内

WPR trace 全量解码（tracerpt -of XML，8.8GB 临时产物已删，证据已归档 `logs/evidence/wpr-probe-evidence.txt`，1,312 条）：

```xml
<Message>TCP: Tcb 0xFFFFAC85B70F0A30 (local=127.0.0.1:63939 remote=127.0.0.1:43723) requested to connect. </Message>
<Message>IP: Transmitting loopback Nbl 0xFFFFAC85E2B37C00. Interface=1, Compartment=1, Src=127.0.0.1:55556, Dst=127.0.0.1:43723, Proto=TCP . </Message>
<Message>IP: Transmitting loopback Nbl 0xFFFFAC85D5C727E0. Interface=1, Compartment=1, Src=127.0.0.1:43723, Dst=127.0.0.1:63941, Proto=TCP . </Message>
```

统计（per 端口）：`Dst=127.0.0.1:<port>` 55 条（Windows→中继的 SYN/数据），`Src=127.0.0.1:<port>` 44 条（中继→客户端的虚拟回应）；`requested to connect` 合计 36 条。

**含义**：Windows TCP 栈正常发出 SYN（Transmitting loopback Nbl），中继也在虚拟回应（反向 Src=端口），但 curl 永不成功（HTTP 000）→ 与阶段七"虚拟握手黑洞"判定完全一致，且这次是在**微软官方日志包内**捕获的。

## 五、pktmon 负结果（重要方法论，防再踩）

- 两个 pktmon（445,657 + 93,192 包）扫描：**中继路径帧 = 0**（无 00:11:22:33:44:55、无 127.x/169.254 源目的 IP）。
- 结论：Consomme 的 loopback 中继在 Windows 侧是用户态栈（wsl_devicehost/dllhost），流量不经过 NDIS/vmswitch 可见组件；**pktmon 对该问题无效**，不要再依赖包级抓包，证据在 ETW（WPR）。
- 附带观察：第一次捕获丢弃率 3%，第二次 18%（17,061/93,192）——窗口内丢弃比例升高，但与探针因果关系未证实（背景流量差异也可能导致），仅记录。

## 七、环境异常：HNS "WSL (Hyper-V firewall)" 创建失败

- `hns_events.log`：每次 WSL 启动（17:53/18:30/18:31/22:18/22:27）都尝试创建 `WSL (Hyper-V firewall)` ICS 网络，Network-Create / Layer-Create / vmswitch 全部 `0x80070002`（文件不存在）。
