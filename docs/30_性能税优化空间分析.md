# 30 性能税优化空间分析（2026-08-20）

> 状态：理论分析，未实验验证。素材备用：正式版复测坐实性能税后，可附官方（简版 L1/L2）。
> 关联：`#41383` 性能预告评论（5351512967）、issue #103、27 号文档性能对照。

## 瓶颈分解（listen 拦截 ~33ms 花在哪）

每次 listen 挂起后，localhost 进程在单线程通知队列（GnsPortTracker::Run）里串行执行：

1. `read_symlink(/proc/{pid}/ns/net)` —— procfs 路径解析 + ns 引用；
2. `GetSocketProtocol(Pid, Socket)` —— 协议探测；
3. `DuplicateSocketFd` = `pidfd_open` + `pidfd_getfd` —— 跨进程 fd 转移（最重的部分）；
4. `ValidateCookie` + `getsockname(dupFd)` —— 验证与端口读取。

内核 seccomp 通知本身为微秒级；重的是"用户空间拿不到 fd，必须跨进程搬运"这一事实。bind 路径同样走 1/3/4，实测 10.2ms——listen 的 33ms 是在其上叠加了协议探测与 getsockname 等操作。

## 优化层次

### L1 用户态微优化（改动小，风险低）
- 缓存 pidfd：同一进程多次 bind/listen 复用 `pidfd_open` 结果（线程退出才失效）；
- ns 检查改 inode 比较：`/proc/pid/ns/net` 的 stat inode 与 m_networkNamespace 比较，替代 readlink 字符串比较；
- 复用已转移的 fd：bind 通知已 pidfd_getfd 过的 socket，listen 通知尝试复用。
- 预期：33ms → 十几 ms 量级（治标）。

### L2 架构级（收益大，风险中）
- listen 改异步注册：已有 sock_diag 观察机制（c_sock_diag_refresh_delay=500ms）可事后发现 implicit autobind 端口，替代同步拦截；代价是首次可达延迟变为 0-500ms 随机；
- 多线程/分区处理通知队列：当前单线程串行是 128 并发放大成 4.27s 的主因，拆分后并发延迟降一个数量级；
- fd→port 缓存：bind 时记录 fd 映射，listen 命中直接放行（需处理 fd 复用竞态）。
- 预期：并发场景 4.27s → 几百 ms，接近消除性能税。

### L3 内核扩展（最优解，成本最高）
- seccomp 通知携带"socket 是否已绑定 + 端口"（内核挂起 listen 时已知 socket 状态）→ localhost 进程免 pidfd_getfd/getsockname/readlink；
- 或"拦截"改"事件通知"（listen 完成时内核主动推事件，不挂起 syscall）→ 同步往返彻底消失。
- 预期：33ms → 微秒-1ms。代价：内核 ABI 变更 + 跨组件协调（seccomp 为通用机制，需微软内部多团队）。

## 现实判断

- 官方短期内大概率不做：正确性修复（`#41051`/`#41125`）已合入；串行单次 43ms 对多数应用无感；高并发场景优先级低；L3 改内核 ABI 风险大。
- 若正式版坐实性能税：回复可附简版 L1/L2 优化方向（2-3 句），展示"现象 + 机制 + 出路"，提升专业度与回应概率。
- 本分析仅理论推演，未在代码层验证每个步骤的相对耗时；若需精确分解，可对 localhost 进程做插桩（非必要，优先级低）。
