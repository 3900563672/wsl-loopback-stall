## 0. 执行摘要（一页看完）

- **现状**：本机 WSL2 存在"新 IPv4 回环端口首连被拒"故障，探针持续 FAIL（错误计数已到 1833 且仍在增长）。初步定位到 WSL localhost 转发中继组件，发现 6 个孤儿 Relay 进程（PPID=1），并发现微软 PR #41252 只修了 create-process 路径、localhost 路径（localhost.cpp:252）仍是"无超时 accept"。
- **目标**：通过一份正式研究，把"推测级"结论升级为"证据级"结论，然后决定：① 是否向微软提 issue；② 如何修正仓库文档与面试详案。
- **核心价值**：如果研究成功并提 issue 被确认/修复，这是**可写进简历的实绩**（"我的报告推动了 WSL 官方修复"），对 Seed SRE 实习面试是稀缺级素材；即使不被采纳，研究本身（因果实验 + 源码分析）也是强面试内容。
- **关键一步**：因果干预实验——kill 6 个孤儿 Relay 后重跑探针。若首连恢复，因果成立，整个故事闭环；若仍失败，假设被推翻，研究转向重新归因（同样有价值，避免提错 issue 打脸）。
- **投入**：4–6 小时，可分 2 周完成。距离面试还有几个月，时间充裕。
- **授权需求**：① kill 孤儿 Relay 实验；② issue 提交；③ 文档修正。三项都等你点头。

## 1. 意义与价值评估（假设我们搞出来了）

### 1.1 五种结局场景矩阵

| 场景 | 定义 | 概率估计* | 面试价值 | 怎么讲 |
| --- | --- | --- | --- | --- |
| A. 微软确认 | issue 被 triage/回复/标记，确认缺陷存在 | 中 | ★★★★☆ | "我向微软报告了 WSL 缺陷，附完整复现，微软确认了" |
| B. 微软修复 | 我们报告的路径被官方修复（PR merged） | 低-中 | ★★★★★ | "我的 issue 推动了官方修复"，简历可写实绩 |
| C. 被无视/关闭 | 无实质回复或被机器人关 | 中 | ★★★☆☆ | 讲研究过程与"如何设计实验验证因果"，诚实说明 |
| D. 自己闭环 | 微软无动作，但我们验证了机制 + 自动化规避 | 高 | ★★★★☆ | "环境组件问题，我做到可发现、可规避、可交接" |
| E. 假设被推翻 | 实验证明与 Relay 无关 | 低 | ★★★☆☆ | "我设计实验推翻了自己的假设"，成长叙事 |

*概率是主观估计：微软 WSL issue 响应不稳定（#41242 从提交到 PR 只用了 2 天，但也有大量 open 数年的 issue）。B 场景概率不高的原因：localhost 路径是否触发官方修复取决于排期，几个月内不一定落地；但 A/D 场景概率高，整体投入产出比良好。

### 1.2 各场景对"面试有多大帮助"的诚实回答

**场景 B（最理想）**：这是可以写进简历、讲 5 分钟的顶级素材。对 SRE 实习岗，面试官看到"实习生向微软提 issue → 官方修复"会立刻确认三件事：① 故障定位能力（你找到了根因）；② 严谨性（复现 + 证据 + 源码引用）；③ 工程素养（规范英文报告、与维护者协作）。这类素材在应届生池子里极其稀缺，因为绝大多数候选人只有课程项目。

**场景 A（很可能）**：弱于 B 但依然强。微软确认 = 你的分析被领域专家背书。"我的报告被微软确认是缺陷"比"我遇到一个环境 bug"高一个量级。面试讲法：把 issue 链接给面试官看，2 分钟讲定位过程。

**场景 D（兜底）**：即使微软不理你，你已经完成了 SRE 的标准动作：影响面评估、因果验证、自动化探针、文档沉淀。这正好是 JD 里"故障分析与解决能力、自动化脚本、文档沉淀"三条的实证。面试讲"我如何验证因果"（kill 实验）比讲"微软没回我"有力得多。

**场景 C/E**：价值不在结果而在过程。C 讲"我把 issue 写到了什么质量"；E 讲"我的实验设计允许自己犯错"——面试官反而更信。但这两个场景的叙事需要更多技巧，面试前要练。

**结论**：研究的期望价值 = P(B)×5 + P(A)×4 + P(D)×4 + P(C/E)×3 ≈ 3.8–4.3 星（5 星制）。对比其他候选素材（告警规则缺陷 ★★★☆、资源校准 ★★★☆），这个案例的**稀缺性和深度都更高**，值得投入。

### 1.3 与目标岗位（字节 Seed SRE 实习）JD 的映射

| JD 要点 | 本研究对应的实证 |
| --- | --- |
| 参与系统稳定性问题排查 | 七阶段排查 + 因果干预实验 |
| 培养故障分析与解决能力 | 组件级定位 + 区分相关/因果 |

| 开源协作（加分项） | 向微软提交规范 issue（英文、复现、源码引用） |

### 1.4 风险清单（提前想清楚）

1. **提错 issue 打脸**（最大风险）：我们的主张 E（localhost 路径未修复）基于主分支源码，但 2.7.8.0 的行为可能不同——阶段 1 校准就是防这个。
2. **因果错位**：孤儿 Relay 与首连失败可能只是伴生关系。kill 实验是防这个。
3. **微软不回复**：概率中。不影响 D 场景价值，但要管理预期。
4. **时间沉没**：研究最大 6 小时，超过就止损。不投入"完全逆向 WSL 二进制"。
5. **环境副作用**：唯一干预是 kill 孤儿 Relay（低风险），全程不 wsl --shutdown、不动 Docker。

## 2. 研究目标与假设

### 2.1 核心假设 H

> 本机"新 IPv4 回环端口首连被拒"由 WSL localhost 转发中继（localhost.cpp 的 RunLocalHostRelay）卡死导致。机制：UtilAcceptVsock 以默认 Timeout=-1 无限等待（poll 60s 超时循环），6 个孤儿 Relay 卡死占用中继资源；该路径未被微软 PR #41252 修复。

### 2.2 可证伪断言清单（研究的对象）

| 编号 | 断言 | 当前状态 | 验证方法 | 推翻条件 |
| --- | --- | --- | --- | --- |
| G1 | 现象真实可复现 | ✅ 已证 | 探针 10/10 FAIL | — |
| G2 | 非业务代码问题 | ✅ 已证 | CI + 对照 + 内核证据 | — |
| G3 | `accept(11)` 的 11 是 SocketFd，非错误码；日志=poll 60s 超时循环 | ⚠️ 半证 | 阶段 1 版本校准 + 源码对照 | 2.7.8.0 的 localhost 路径有超时 |
| G4 | 存在 6 个孤儿 Relay（PPID=1、纯 Relay 名） | ✅ 已证 | ps 快照 | — |
| G5 | 孤儿 Relay 与首连失败有因果关系 | ❌ 未证 | 阶段 2 kill 实验 | kill 后仍失败 |
| G6 | 微软 PR #41252 未覆盖 localhost 路径 | ⚠️ 半证 | 阶段 1 版本校准 | 主分支或 2.7.8.0 已修 localhost |
| G7 | 现有 issue 无精确覆盖我们症状面 | ⚠️ 半证 | 阶段 4 全读 + 补搜 | 找到完全一致的报告 |
| G8 | 故障起点 11:38 与环境事件（睡眠/重启/负载）相关 | ❌ 未证 | 阶段 1 事件时间线 | 无对应事件（但非必须） |

### 2.3 研究的成功标准（注意：不是"证明 H 对"）

1. G1–G7 全部升级为 ✅ 或 ❌（明确结论，不留"可能"）。
2. 产出研究报告：假设、实验记录、证据、结论、局限（哪些没验证、为什么）。
3. 产出文档修正清单：仓库 4 处 + 面试详案 1 处，每处写明"原文 → 新文 → 依据"。
4. 产出 issue 提交决策建议（提 / 在 #41286 下追加 / 不提，附理由）。
5. 无论 H 成立与否，研究报告都有明确的"结论和下一步"。

### 2.4 研究边界（明确不做的事）

- 不 wsl --shutdown、不重启、不动 Docker、不改业务代码。
- 不做内核调试/eBPF 深挖（除非 dmesg 干净，否则没必要）。
- 不尝试完全逆向 WSL 二进制（版本对照用官方源码 + tag 即可）。
- 不无限扩大 issue 阅读范围（阶段 4 限定在 8 个已知相关 issue + 2 轮关键词补搜）。

## 3. 详细研究计划（六阶段）

> 每阶段统一结构：目标 / 输入 / 步骤 / 输出 / 验收标准 / 预计时长 / 风险。所有命令在 WSL 内执行（Ubuntu），Windows 侧只读。

### 阶段 0：证据盘点与复核（30 分钟）

- 目标：确认已有证据 E1–E9 哪些仍然有效、哪些需要重验（环境可能变化）。
- 步骤：
  1. 重跑探针，记录输出与错误计数（当前 1833）。
  2. 复核四地址对照（127.0.0.1 / 127.0.0.2 / eth0 / [::1]），确认结果与 08-18 一致。
  3. 复核 /proc/net/tcp 同时刻证据是否可重复。
  4. 更新证据表：每项标注"复核时间 + 结果"。
- 输出：E1–E9 复核表。
- 验收：全部证据要么带新时间戳确认，要么标记"已失效"。
- 风险：环境被重启后故障消失 → 记录"消失"也是一种结论（说明是环境状态问题），研究转入"复现条件"调查。

### 阶段 1：版本与基线校准（1 小时，最关键的防打脸步骤）

- 目标：确认我们引用的源码（主分支 1e14a49）与**本机实际运行版本 WSL 2.7.8.0** 的对应关系，确认 G3/G6。
- 步骤：
  1. `wsl --version` 全量输出存档（含 WSLg、MSRDC、DXCore、Windows build）。
  2. 确认 2.7.8.0 的发布日期与对应源码 tag：查 microsoft/WSL 的 tags/releases，找到 2.7.8.0 对应的提交；若找不到精确 tag，用"最近发布说明 + release 时间"推断。
  3. 在该 tag 上核对：`src/linux/init/util.cpp` 的 UtilAcceptVsock 实现（poll 60s 逻辑是否一致）、`localhost.cpp:252` 调用是否仍是两参数（Timeout=-1）、246 行是否正是 "Waiting for abnormally long accept"（验证我们 dmesg 行号 246 与源码一致）。
  4. 确认 PR #41252（merged 08-05）是否包含在 2.7.8.0 内：查 2.7.8.0 release 时间（若晚于 08-05 则包含）；用 `git log --oneline --grep="timeout to create process"` 在主分支找提交，看其父提交与 2.7.8.0 tag 的关系。
  5. 查主分支自 1e14a49 之后 localhost.cpp / util.cpp 有无后续修改（`gh api` commits 列表），确认"当前主分支仍未修 localhost 路径"是否成立。
  6. 收集故障起点环境事件：系统启动时间（dmesg）、首错时间（boot+43695s）、期间是否有睡眠/唤醒（`journalctl --since` 或 Windows 事件日志只读）、用户操作记录（重启过）。
- 输出：版本对照表（2.7.8.0 ↔ tag ↔ 主分支）、PR 归属结论、事件时间线。
- 验收：能明确回答"我们 dmesg 的行号 246 与 2.7.8.0 源码是否一致"和"PR #41252 是否覆盖 localhost 路径"。
- 风险：2.7.8.0 找不到精确 tag → 用 release notes + 相邻 tag 推断，并在研究报告中标注"推断"。

### 阶段 2：因果干预实验（30 分钟，核心实验，需授权）

- 目标：验证 G5——孤儿 Relay 与首连失败是否有因果关系。
- 设计（单变量干预，最简可判）：
  1. 预实验（5 分钟）：记录探针结果、错误计数、孤儿 PID 列表（ps 快照存档）。
  2. 干预：`kill` 6 个孤儿 Relay（PID 833511 / 1283916 / 1428884 / 1428979 / 1429041 / 1437624）。它们 PPID=1、无父会话，属可清理进程；不涉及 wsl --shutdown，不影响其他发行版与 Docker。先 `kill -0` 确认存活，再 `kill`（SIGTERM），5 秒后检查是否退出。
  3. 观察（关键）：kill 后立即跑探针 10 轮 + 观察 dmesg 新错误是否停止。判定：
     - 探针恢复 PASS 且错误计数停止增长 → **因果成立**（H 强化），记录恢复时间。
     - 探针仍 FAIL → **因果不成立或部分成立**（H 被削弱），记录，转入重新归因（观察新生成的 Relay、检查 Windows 侧 wslrelay）。
  4. 对照记录：kill 前后各 5 分钟的错误计数斜率对比。
  5. 备注：如果 WSL 自动重建 Relay，观察新 PID 是否工作正常（这本身是重要信息：重建后是否恢复）。
- 输出：干预实验记录（前后对比数据 + 判定）。
- 验收：能明确回答"kill 后是否恢复"，附数据。
- 风险：低。唯一注意：不 kill 名字带子 PID 的活跃 Relay（Relay(135764) 这类是正常工作的）。**需用户授权。**

### 阶段 3：深度观测（1 小时，支撑因果与机制）

- 目标：把"时间相关"升级为"时间对齐"，并观察机制细节。
- 步骤：
  1. 时间对齐采样：每 30 秒记录一次 {探针结果, dmesg 错误计数, 孤儿 Relay 数量}，持续 30 分钟，画出三者的时间线（手写脚本输出 CSV 即可）。
  2. /proc/net/vsock 快照：记录 vsock 端口与进程对应关系（ps + ls -l /proc/<pid>/fd 对照），确认 6 个孤儿 Relay 各自绑定的 vsock socket。
  3. 孤儿 Relay 详情：`ps -o pid,lstart,etime,stat` 看启动时间（应早于 11:38 前后或当时重建）、状态（S/D/R）。
  4. fd 与内存：`ls /proc/<pid>/fd | wc -l` 与 RSS，确认"不是 fd 耗尽"（G3 旁证）。
- 输出：CSV 时间线、vsock 对照表、进程详情表。
- 验收：能回答"失败与错误计数、孤儿数量是否同步变化"。
- 风险：采样脚本简单，注意不引入负载（每 30s 一次足够）。

### 阶段 4：症状面比对（1 小时，决定 issue 怎么提）

- 目标：验证 G7，并提炼"我们的独特点"作为 issue 的核心主张。
- 步骤：
  1. 全读 8 个相关 issue（含全部评论）：#41242、#41286、#40650、#40795、#13864、#13740、#8677、#12837。用 `gh api .../comments` 拉评论。
  2. 建四维对比表：症状 / 环境 / 日志 / 恢复方式。
  3. 补关键词搜索（各 1 轮）：`localhost relay refused`、`port-forward connection refused WSL`、`wsl localhost new port`、`UtilAcceptVsock waiting abnormally`。
  4. 提炼独特点（预期结论）：现有 issue 症状集中在"新会话失败/挂起"，我们的症状是"localhost 新端口注册失败但会话/业务正常"，且我们有探针复现 + 对照实验 + 孤儿 PID 清单。
- 输出：对比表 + 独特点清单 + "提 issue / 追加评论 / 不提"建议。
- 验收：能明确回答"我们的症状面是否被现有 issue 覆盖"。
- 风险：issue 评论可能很长，限时 1 小时，用摘要表承载。

### 阶段 5：结论与文档修正清单（1 小时）

- 目标：汇总研究结论，产出修正清单（先不动手改，等你审）。
- 步骤：
  1. 按 G1–G8 逐条写最终判定（✅/❌/⚠️ 及依据）。
  2. 修正清单（预期内容）：
     - docs/journal/2026-08-18-wsl-loopback-relay.md：删"错误码 11=EAGAIN"表述 → 改为"fd 11，poll 60s 超时循环（Timeout=-1 无超时 accept）"；补充孤儿 Relay 证据与 kill 实验结论。
     - docs/operations/WSL_LOOPBACK_CASE_STUDY.md：同上修正 + 官方佐证章节改为 #41242/#41286/PR #41252 的准确引用（#12837 降级为"曾误引"并说明）。
     - docs/lessons/process-wsl-loopback-fresh-listen-refused.md：机制描述修正。
     - docs/operations/TROUBLESHOOTING.md §3.3：日志解读修正。
     - Documents/WSL回环案例_面试详案.md：机制、证据链、Q&A 中"EAGAIN"相关表述全部修正，官方佐证章节重写。
  3. 每个修正点附"依据"（研究报告章节号）。
- 输出：修正清单（评审稿）。
- 验收：每处"原文→新文→依据"三要素齐全。

### 阶段 6：交付决策（30 分钟，等你拍板）

- 目标：基于阶段 2/4/5 的结论做三个决策。
- 决策树：
  1. G5 因果成立（kill 后恢复）→ 建议向微软提交（走 7.1 的提交标准）；因果不成立 → 暂不提，先重新归因。
  2. G7 症状面未被覆盖 → 提新 issue（cross-link #41286/#41242）；被覆盖 → 在 #41286 下追加评论补充证据。
