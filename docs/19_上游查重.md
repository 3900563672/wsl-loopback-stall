## 一、结论摘要

1. **"TCP retry / timeout 逻辑未实现"是 openvmm 官方自己承认的 backlog**（issue #2313），TimeWait 定时器 TODO 从开源首日（2020 整体导入）就在。

3. **我们发现的"Consomme 模式 + TCP 回环 churn 的同步注册链 / 60s 窗口 / 黑洞"机制组合，无人以源码层报告过**——现有报告要么是现象级，要么是 mirrored/UDP/relay 模式，与我们的场景不重叠。

## 四、我们的独特贡献（无人覆盖）

1. **Consomme 模式 + TCP 回环 churn**：同步注册链（seccomp 挂起进程 → GNS → 全局排他锁 → BindPort）导致 bind 延迟/首连失败的具体机制链，无人报告。
2. **60s 去分配窗口（c_bind_timeout_seconds=60）与 TIME_WAIT / 无 SO_REUSEADDR 的交互**：端口关闭后 Windows listener 保留 60s、重绑失败窗口（WSAEADDRINUSE）——无人提过。
3. **connect 超时静默不发 RST（handle_connect_error）**："虚拟握手黑洞"的代码级机制——无人提过。
4. **禁 SYN 重传（SIO_TCP_INITIAL_RTO）在回环代理场景的放大效应**——无人提过。

## 五、查重结论与建议

1. 我们的主题聚焦"Consomme 模式 TCP 回环的瞬态/黑洞机制链"，与 #41162（mirrored/UDP）、#40803（IPv6 泄漏）、#4851（relay 双栈）明确区分，引用它们作为"端口跟踪领域官方已知活跃"的背景。
2. 引用 openvmm #2313：证明"TCP retry/timeout 未实现"是官方待办，我们的贡献是展示其在 WSL 集成场景（同步注册链 + 60s 窗口）的可观察影响。
3. 同领域官方已知项：#41162 / #40803 / #41125（查重时确认，作为背景引用）。
4. 对比：#41162 的提交者已用源码级分析（含 GnsPortTracker 行号）；本案例证据链由 16 号文档 + 实验数据构成，侧重点可区分。
