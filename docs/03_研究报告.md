# WSL localhost 转发研究——研究报告

> 日期：2026-08-18 | 状态：定稿（阶段 5）| 存放：Documents/（不入库）
> 目标：把推测级结论升级为证据级结论；本报告支撑 issue 决策与文档修正。

---

## 1. 核心结论（先给结论）

**本机现象：新 IPv4 回环端口首连被拒（WSL 内立即连接失败 + Windows 侧对新端口永远不可达），长存活端口、eth0、IPv6 正常。** 经因果实验验证，**故障核心是 WSL2 localhost 转发链路的"新端口注册"永久失效**，而不是最初怀疑的"Relay 进程卡死"。

关键修正（与 08-18 下午的旧结论对比）：

| 项 | 旧结论（推测级） | 新结论（证据级） |
| --- | --- | --- |
| dmesg `accept(11)` | "错误码 11 = EAGAIN，accept 停滞" | **11 是 SocketFd**；日志语义 = poll 60s 超时循环（Timeout=-1 无超时 accept），2.7.8 源码 util.cpp:246 精确对应 |
| 故障源 | "localhost 转发中继（Relay）组件降级" | **Relay 不是故障源**；kill 全部 stuck Relay 后故障不变。Relay 的 poll 超时日志是**症状**（等不到 vsock 连接） |
| 真实故障 | 未定位 | **新端口注册链路失效**：WSL 内新端口延迟后可访问（loopback 正常），Windows 侧等 11 秒仍不可达（注册永不完成）；长存活端口注册早已完成故正常 |
| 微软修复 | "PR #41252 只修 create-process，localhost 未修" | 成立且更精确：2.7.8 与 master 的 localhost.cpp 均无超时调用；但**该无超时与本故障无因果**（relay 只是等待者） |

## 2. 假设与判定

原假设 H（Relay 卡死导致首连失败）**被实验推翻**。判定表：

| 断言 | 判定 | 依据 |
| --- | --- | --- |
| G1 现象真实可复现 | ✅ | 探针持续 10/10 FAIL；多时间点复现 |
| G2 非业务代码 | ✅ | CI 全绿；四地址对照；Python 复现；内核证据 |
| G3 日志语义（fd 11 / poll 60s / 行号 246） | ✅ | 2.7.8 tag 源码逐行核对（util.cpp:202-260） |
| G4 存在孤儿 Relay | ✅ | ps：6 个 stuck（PPID=1 或 SessionLeader 下，纯 Relay 名） |
| G5 孤儿 Relay ↔ 首连失败有因果 | ❌ **推翻** | kill 全部 stuck Relay（SIGTERM 被忽略 → SIGKILL）后：dmesg 错误停止、探针仍 10/10 FAIL、Windows 侧仍不可达 |
| G6 微软 PR #41252 未覆盖 localhost 路径 | ✅ | PR diff 只有 init.cpp 一行；master localhost.cpp:252 仍两参数调用 |
| G7 现有 issue 无精确覆盖我们症状面 | ✅（见 §5） | #41242/#41286 症状是"新会话失败"；我们是"新端口注册失效，会话正常" |
| G8 故障起点 11:38 与事件相关 | ⚠️ 存疑 | dmesg 现存最早 46260s（12:20）；11:38 为交接记录不可复核 |

## 3. 实验记录（按时间顺序）

### 3.1 阶段 0：证据复核（18:0x）
- 探针 10/10 FAIL，错误计数 1866（增长中）。
- 四地址对照：127.0.0.1 0/10（refused）、127.0.0.2 0/10（timeout）、eth0 10/10、[::1] 10/10（**修正探针 bug 后**：原 nd_addr.go 对 IPv6 重复括号）。
- 内核证据：/proc/net/tcp=0A（LISTEN）同时刻 connect refused。
- iptables-save 为空（环境变化：16:2x 时还有 Docker 规则）→ 无防火墙拦截。
- 孤儿 Relay fd 数 13–16 稳定 → 排除 EMFILE。
- Windows→WSL 长存活 8080 → HTTP 200。

### 3.2 阶段 1：版本与源码校准（18:10）
- 本机：WSL 2.7.8.0（release 2026-06-06）、内核 6.18.33.1、Ubuntu 26.04、Windows 26200.9168。
- 2.7.8 tag（95669d3）源码：
  - util.h:121 `Timeout = -1` 默认
  - util.cpp:202-260：`while(true)` + `poll(..., 60*1000)`；246 行 `LOG_ERROR("Waiting for abnormally long accept({})", SocketFd)` —— **与本机 dmesg 行号 246 完全一致**；格式化串只传 SocketFd → `accept(11)` 的 11 是 fd。
  - localhost.cpp:52：`UtilAcceptVsock(listenSocket, hvSocketAddress)` 两参数 → 无超时。
  - init.cpp:1474：create-process 路径同样无超时（PR #41252 改的正是这行）。
- PR #41252：merged 2026-08-06，diff 仅 init.cpp 一行（加 SESSION_LEADER_ACCEPT_TIMEOUT_MS）。
- master 现状：localhost.cpp:252 仍两参数（未修）；util.cpp:254 日志仍在。
- 结论：2.7.8 不含 PR #41252；localhost 路径主分支至今未修。

### 3.3 阶段 2：kill 因果实验（18:15，决定性）
- 预实验：6 个 stuck Relay（833511/1283916/1428884/1428979/1429041 PPID=1；1437624 PPID=SessionLeader 135683）。
- 干预 1：`kill -15` 5 个 PPID=1 孤儿 → **全部忽略 SIGTERM**（#41242 所述 stuck relay 特征）。
- 干预 2：`kill -9` 全部 6 个 → 全部退出。
- 结果：dmesg 错误计数停止增长（1883 → 稳定）；**探针仍 10/10 FAIL**；WSL 内新端口延迟 2 秒后可访问。
- 判定：**G5 推翻**。Relay 进程卡死不是首连失败的因；dmesg 日志是症状（relay 等不到 Windows 侧发来的 vsock 连接）。

### 3.4 阶段 2b：Windows 侧可达性实验（决定性新证据）
- WSL 内起 python http server（新端口 18443/18466），WSL 内 curl → 200（loopback 正常）。
- Windows 侧 curl：等 2 秒 → 000；等 11 秒 → **仍 000**。
- 对照：Windows 侧长存活 8080 → 200。
- 判定：**新端口注册永不完成**（不是变慢）。转发链路中"新端口注册"环节失效；已有注册的端口转发正常。

## 4. 修正后的因果模型

```text
WSL 内 listen 新端口（127.0.0.1）
        │
        ▼
guest 侧 port tracker 捕获 bind/listen ──vsock──► Windows 侧 wslservice 注册转发
        │                                                │
        ▼                                                ▼
   （注册完成前，WSL 内立即连接被拒，            【故障点】注册请求不被处理：
    Windows 侧不可达）                             新端口永远不注册
                                                       │
                                                       ▼
                                               relay 收不到 vsock 连接
                                               → poll 60s 超时 → dmesg 日志（症状）
```

- 故障点位置（guest 侧 tracker / vsock 通道 / Windows 侧 wslservice）**未最终区分**——受限于 Windows 侧不可观测性，列为局限。
- 与 #41286（hvsocket new-session transport dies）/ #40650（vsock 连接数高时 accept4 failed 110）同族：**"新"连接/注册失效、已有连接继续工作**。

## 6. 局限（诚实声明）

1. Windows 侧 wslservice 内部不可观测（无相关事件日志、无 wslrelay.exe 独立进程）→ 故障点未最终定位到"guest tracker vs vsock vs wslservice"。
2. 故障触发条件未知（11:38 起点不可复核；无终止/sleep 的直接证据；用户曾整机重启过）。
3. 未做 `wsl --shutdown` 恢复验证（需用户授权，影响环境）。
4. kill 实验只证明"relay 进程非因"，未排除"relay 缺席后注册仍坏"的其他机制（已由 Windows 侧实验覆盖主路径）。

## 9. 恢复验证后的结论修正（2026-08-18 晚，最终版）

经用户授权执行 `wsl --shutdown` 恢复验证，**推翻了本报告早期两处结论**（诚实记录如下）：

### 9.1 旧探针推翻（H1 健康对照）
- 健康态新端口注册延迟实测 50–100ms；`t=0` 立即拨号 ×10 健康态也必然 FAIL。
- 早期"E1/E3a/E3b 0/10 失败"读数属**探针设计缺陷**，全部作废；不能作为故障证据。

### 9.2 vsock 探针推翻（H2/H2b）
- 对未监听端口 vsock connect 超时（ETIMEDOUT）是**正常行为**；早期 A2"guest→host vsock 失效"结论撤销。
- 已知存活端口 50000/50001/50002/50005 全部 CONNECTED → vsock 通道活着。

### 9.3 健康态瞬态（新发现）
- 同一进程内连续端口 churn：第 1 轮必过，**第 2 轮起注册停滞 >2s，2–5s 自愈**（5/5 复现；进程内间隔 3s 仍失败，独立进程 1s 间隔全过 → 会话拆除竞争）。
- 全程 dmesg 计数 = 0 → 与严重形态（dmesg 持续报错、Windows 侧不可达、小时级）是**两个独立形态**。
- 可作微软 issue 的 **Repro from healthy**。

### 9.4 仍有效的严重形态证据（最终清单）
- Windows 侧新端口 curl ≥10s 仍 000（Windows 侧注册未落地）
- Windows netstat 无新端口（A1 有效）
- 长存活 8080 正常（E9 有效）
- 复用端口可注册（有效）
- dmesg `UtilAcceptVsock` 持续增长（症状计数，非因果）

### 9.5 因果模型修正（最终）
- 严重形态因果：localhost 转发新端口**注册链路失效**（Windows 侧证据）→ relay poll 超时日志为**症状**，relay 进程卡死为伴生现象。
- 健康态瞬态因果：进程内会话拆除竞争 → 注册停滞 2–5s 自愈（与 dmesg/严重形态无关）。
- 探针语义：单轮 + 时延测量 + Windows 侧 curl 校验（健康态 PASS）；多轮仅诊断，结果不能判定故障。
