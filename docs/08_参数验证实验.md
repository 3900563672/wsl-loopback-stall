## 实验 1：bind() 系统调用耗时（GNS 同步注册链延迟）

### 结果

| 场景 | min | p50 | p95 | max | avg |
| --- | --- | --- | --- | --- | --- |
| seq 200 轮（127.0.0.1） | 2.4ms | 10.4ms | 21.5ms | 33.5ms | 13.7ms |
| churn 8×200 轮（127.0.0.1） | 43.4ms | 93.3ms | 93.9ms | 126.1ms | 90.4ms |
| syscall 对照 getpid | - | 83ns | - | - | - |
| syscall 对照 socket+close | - | 1.08µs | - | - | - |
| syscall bind 127.0.0.1 | 471µs | 10.4ms | 21.3ms | 21.9ms | - |
| syscall bind 127.0.0.2 | 5.0ms | 10.4ms | 20.9ms | 31.7ms | - |

### 结论

- **每个 bind 系统调用固定 ~10.4ms 往返开销**（对照：无拦截的 socket+close 仅 1µs，相差 1 万倍）——即 GNS 同步注册链（seccomp 挂起 → localhost 进程 → GNS 通道 → Windows 排他锁 → 确认返回）的实测往返延迟。
- 127.0.0.2 同样 ~10.4ms：guest 侧 seccomp 拦截所有 bind()（不分地址），Windows 侧才区分 127.0.0.1（源码 HandlePortNotification "Only intercepting 127.0.0.1" 指 Windows 侧处理逻辑，不是拦截范围）。
- **churn 8 并发：p50 93ms ≈ 8×10ms 串行排队**——全局排他锁 + 同步链的积压效应实测确认。
- 健康态无 >1s；秒级停滞需要更大并发或故障路径（Windows BindPort 失败重试等）。

## 实验 2：去分配窗口（c_bind_timeout_seconds=60）行为

### 2a：bind → close → 立即重 bind → 保持 → close

- Windows listener 全程 LISTENING（重 bind 后端口活跃 → 超时清空 → 永续）
- 最终 close 后 **~1.4s 内 listener 消失**

### 2b：bind → close → 不重 bind → 观察 70s

- close 后 **~1.8s 内 listener 消失**（netstat 2s 轮询粒度）

### 结论（修正 20 号文档推断）

- **listener 在 close 后 <2s 即释放，不是 60s**。
- c_bind_timeout_seconds=60 的真实作用：**bind 完成后、sock_diag 首次确认端口活跃之前的竞态保护窗口**（防止 sock_diag 刷新先于 bind 完成而误释放）。一旦 sock_diag 确认活跃（超时清空），close 后立即释放；重 bind 也会清空超时。
- **20 号文档 3.8 节"端口关闭后 Windows listener 保留 60s"推断错误，已修正**（诚实记录：推断被实验推翻）。
- "有连接历史端口保留 60-75s（CloseWait + WSAEADDRINUSE）"的重新归因：不是 listener 保留，而是 **Windows 侧连接 socket 的 TIME_WAIT 残留 + create_bound_socket 无 SO_REUSEADDR** → 端口快速重 bind 时 WSAEADDRINUSE。60-75s 更接近 Windows loopback 连接 TIME_WAIT 的实测值（非默认 240s，待抓包确认）。此点需抓包验证，见待办。

## 实验 3b：TIME_WAIT 时长与同四元组重连（netstat 实测，2026-08-19 补充）

### 服务端主动关闭（45681，close 顺序：服务端先 FIN）

- 00:28:26.635 服务端 close → 00:28:28 起 netstat 见 `127.0.0.1:45681 127.0.0.1:55551 TIME_WAIT`
- 00:29:47 仍在 → 00:30:27 消失：**TIME_WAIT 持续约 81~121s**
- 期间 WSL 重新 bind 45681（wildcard listener）**1.3s 即成功**——listener bind 不与 TIME_WAIT 连接 tuple 冲突

### 客户端主动关闭（45682/55552，close 顺序：客户端先 FIN）

- 00:31:58.878 客户端 close → 00:31:58.906 客户端 tuple `55552→45682` 进入 TIME_WAIT
- 同四元组重连（SO_REUSEADDR 绑定 55552 后 connect）：**全程 WSAEADDRINUSE(10048)**，150s 超时仍未恢复
- 00:34:29（+145s）仍失败 → 00:35:0x 消失：**TIME_WAIT 持续约 145~187s**
- 结论：TIME_WAIT 期间同四元组 bind/connect 必失败（无 SO_REUSEADDR），"60-75s"旧推断修正为 **81~121s（服务端主动关闭）/ 145~187s（客户端主动关闭）**，均低于默认 TcpTimedWaitDelay(240s)

## 实验 4：极端 churn——秒级停滞定量复现（2026-08-19 补充）

工具：churn_heavy.go（并发可配，统计 >1s 停滞比例）

| 并发 | 轮数 | p50 | p95 | max | >1s 占比 | 吞吐 |
| --- | --- | --- | --- | --- | --- | --- |
| 64 | 100 | 666ms | 687ms | 735ms | 0% | 96 bind/s |
| 128 | 100 | 1.322s | 1.355s | 1.420s | **99.27%**（12707/12800） | 96 bind/s |

- p50 ≈ 并发数 × 10.4ms：与全局排他锁 + 同步链串行模型完全吻合（64×10.4=666ms，128×10.4=1.33s）
- 吞吐恒定 ~96 bind/s（= 1/10.4ms）：**任何并发下总吞吐不变，延迟随并发线性放大**
- "秒级停滞"在 syscall 层定量复现：>100 并发即有 >99% 的 bind 超 1s——与项目里 100+ Pod 才触发的现象一致

## 实验 5：抓包级验证（WPR/ETW 管理员权限，2026-08-19 补充）

工具：wpr（Microsoft-Windows-TCPIP + Kernel-Network，27MB ETL）+ Get-WinEvent 解析

### 5a 健康态同四元组重连（T1，SO_REUSEADDR 绕过 bind 冲突）

两次复现（55554/55556），WPR 事件序列：

```text
TCP: endpoint ... (sockaddr=127.0.0.1:55556) bound.        # SO_REUSEADDR bind 成功
TCP: Tcb ... (local=127.0.0.1:55556 remote=127.0.0.1:45684) requested to connect.
TCP: listener ... accept failed: connection insertion. Duplicate TCB = 0x...
TCP: connection ... connect attempt failed with status = 无法打开已存在的传输地址。
```

- 两次均在 **12ms 内失败，SYN 从未发出**（请求后无 "Transmitting loopback Nbl"）
- 健康态"黑洞"的真实形态：Windows TCPIP 在 TCB 插入阶段直接拒绝重复四元组（WSAEADDRINUSE），不是 SYN 被 challenge ACK
- 5/8 次基线连接 0ms 完成、SYN/SYN-ACK 各 1 次（无重传需求）

### 5b 默认 Windows loopback SYN 重传对照

- 抓包期间本机其他进程对 127.0.0.1:8080 的连接：`retransmitting connect attempt, RexmitCount = 4`，RTO 300ms→6s 退避——**默认 Windows TCP 会重传 SYN**
- 与 Consomme 路径源码级 `SIO_TCP_INITIAL_RTO`（禁重传）形成对比：Consomme 创建的对端 socket 在黑洞时无重传兜底 → 连接挂死直到应用超时
- 注：禁重传本身为源码级证据（锚定 0bb5cf75），退化态抓包未完成（见遗留）

### 5c churn 期间的 Windows 侧端点事件（开放观察）

- 128×50=6400 次 WSL bind 期间，Windows 侧 BindEndpoint(WFP) 事件仅约 744 个（11.6%），时间上散布整个 churn
- 疑点：部分 WSL bind 未创建新 TCPIP 端点（wsldevicehost 端点缓存/复用？），**未定论，留待后续验证**
