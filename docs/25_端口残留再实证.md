# 25 开发环境端口残留再实证（2026-08-20）

> 状态：已完成——"端口被遮蔽后换全新端口立即恢复"规律在开发环境中第 N 次实证；同时记录一个半死进程造成的假象与两条操作教训。

## 一、事件背景

本地开发预览使用 `python3 mock-server.py <port>`（ThreadingHTTPServer 静态服务，构建产物 + API fixtures）。当日服务端口为 4180，期间因代码迭代多次重启。

## 二、事件时间线（2026-08-20 上午）

| 时间 | 操作 | 观察 |
| --- | --- | --- |
| 09:40 | 重启 4180（kill 旧进程后 setsid 新起） | 成功监听，正常服务 |
| 09:44 | 服务代码引入递归 bug（`serve_configuration` 自递归） | 每个 `/configuration` 请求线程抛 `RecursionError`；ThreadingHTTPServer 的 serve_forever 主循环存活，进程未退出 |
| 09:46 | 修复代码后再次启动 4180 | `OSError: [Errno 98] Address already in use`；但 `ss -tln` 仍显示 `0.0.0.0:4180 LISTEN` |
| 09:46–09:47 | 继续请求 4180 | 仍能收到响应（旧代码路径的 TypeError traceback），端口"看起来活着" |
| 09:47 | `pgrep -f` 强杀残留进程，改起全新端口 4181 | 立即监听成功；持续服务 90+ 请求（含 200KB 级大响应、并发 SSE 长连接）无异常 |

## 三、观察与既有结论的关系

- **与"端口被遮蔽、换全新端口立即恢复"的既有规律完全一致**（该规律自 08-18 起已在开发中反复出现：4173 → 4180 → 4181 均为同一模式）。
- 本次补充一个**区分细节**：`bind` 报 `EADDRINUSE` + `ss -tln` 显示 LISTEN 有两种来源——
  1. 真正残留的端口表项（此前已证实的 Consomme 注册链失效形态）；
  2. 半死进程：请求线程全部崩溃、`serve_forever` 主循环仍存活，端口仍被该进程持有（本次 09:44–09:47 的形态）。
  - 区分方法：`ss -tlnp`（root）或 `pgrep -f` 确认是否有存活进程；有进程 → kill 后重试；无进程仍 EADDRINUSE → 换新端口。
- 未发现与上游 #41383 根因（新端口注册链失效）冲突的新证据；本次是同一现象在工程侧的影响面补充：**预览/开发服务在端口异常时应优先换新端口，而不是反复重启同一端口**。

## 四、操作教训（已实测）

1. `pkill -f "python3 mock-server.py 4180"` 会匹配到**执行该命令的 shell 自身**（bash -lc 的命令行包含相同字符串）→ 把自己杀掉，后续命令不执行。正确姿势：`pgrep -f "[m]ock-server"`（方括号避免自匹配），或按端口找 pid。
2. 非 root 下 `ss -tlnp` 不显示 pid 列（权限不足），拿不到目标进程号时用 `pgrep` 兜底。
3. 端口被遮蔽后在同一端口反复重试启动会持续失败并产生误导性日志；换全新端口（+1 或随机）通常立即恢复。

## 五、结论

- 开发环境复现成本极低（半小时内多次触发），与探针驱动复现互为印证：该问题不是偶发环境噪音，而是 Consomme 端口注册链在"高频重启 + 同端口短连接"下的稳定行为。
- 建议在开发工具链中固化为习惯：**端口异常 → 换端口**（frontend-redesign 的 DEV-NOTES 已记录）。
